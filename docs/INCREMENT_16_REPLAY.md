# Increment 16: private integrated replay

This procedure prepares a new, bounded synthetic run. It does not clear the existing Google Sheet, mutate Calendar, send mail, or claim connected results. The six scenarios in `scripts/demo_replay.mjs` get a unique run ID; record the actual request, session, person-case, Form, event, proof, message, and receipt IDs only after observing them.

## Prepare

1. Work from the reviewed release commit. Verify the dedicated owner, deployment, demo Sheet, current scopes, and four-account test allowlist in the ignored private configuration. Confirm the production matrix is not the target. Keep the current evidence and record its existing folder/Sheet export in `reset.previousEvidenceSnapshot` before considering any reset.
2. Run `node scripts/demo_replay.mjs prepare` to validate the ignored dedicated fixture without writing anything. Then run `node scripts/demo_replay.mjs prepare --write` to create a new `data/demo-replays/RUN-.../run-record.json`. Both commands are local. The output directory and its account addresses are ignored by Git.
3. Use **fresh request IDs** for the six scenarios. Do not call `resetDemoFixture()` on a Sheet holding prior evidence: it rewrites the synthetic catalog and skill rows. If a clean Sheet is essential, first export the old Sheet and related evidence, confirm a separate new dedicated demo Sheet and owner, then use a separately reviewed connected seed procedure. Record both target IDs. Never point this workflow at the production matrix.
4. Run `node scripts/demo_replay.mjs verify data/demo-replays/RUN-.../run-record.json` after each scenario. Use `--fixture <path>` if the private fixture is in another ignored `data/` path. Exit 1 means missing observations or a rule violation; the JSON output distinguishes `pending` from `violations`. Verification compares the fixture fingerprint and four-address allowlist, then hashes any local PDF named in `archivePairs` against the recorded Drive and local SHA-256 values. A local hash match alone does not prove that the Drive object still exists: open or export the Drive copy during connected replay and record the evidence.

The run record is the private evidence index. Keep generated links, addresses, screenshots, exports, and logs there or under the same ignored run directory. Do not commit it. Enter observed facts only; leave unknown fields as `null`. Preparation records the Git source commit; enter the actual `deploymentId` and numbered `deploymentVersion` after confirming the reviewed source was deployed. `boundary.productionMatrixUntouchedEvidence` should point to a read-only before/after comparison or an equivalent checked audit record, while `ownerChecked` records inspection of the dedicated owner. Use the actual demo Sheet ID. Record every outbound mail and Calendar recipient under each scenario's `outbound` as `{ "type": "email" | "calendar", "recipients": ["..."], "evidence": "private capture or ledger reference" }`. Passed scenarios require the relevant outbound types and nonempty recipients. For a passed eligibility-only scenario with no outbound action, record `noOutboundEvidence` with a reason and a private capture reference. The verifier rejects addresses outside the four-account fixture allowlist.

## Scenario script

| Scenario | Actions and required observation |
| --- | --- |
| Group success | The baseline marks `SUMNER` excluded for `TC_R033`. After preserving prior evidence, apply and log the planned **demo-only** `–→0` correction, then select both synthetic participants, group mode, varied free slots, and one shared event. Complete each assigned trainer and participant Form, then make separate proofs and verified dual archives. Confirm a single request notice after both person cases finish. Replay booking, proof, skill update, and notice actions to check idempotency. |
| Individual progression | Select `TC_R030` for a level-0 participant. Assign an eligible level-4 individual trainer. Complete theory and practice in order; confirm level 0→1 exactly once. A second completion action must not raise to level 2. |
| Matrix block/correction | Show a skipped level block on a progression topic and the blank-cell block for `WOHNUNG` on `TC_R077`. Correct only that blank demo cell to `0`, record before/after and actor, then retry at target 1. Use a separate waiting demo case for the conflict gate; an intervening Sheet level change must not be overwritten. Record both request IDs. |
| Group decline/no RSVP | The baseline has `SUMNER` at level 0 for `TC_R027` while `WOHNUNG` is at 1. After preserving prior evidence, apply and log the planned **demo-only** `0→1` correction, then book a group theory event at target 2. Decline for one synthetic participant and leave another unanswered; show the per-person flags and unchanged group event. Check the unanswered flag on the preceding business day. Do not infer attendance from either RSVP state. |
| Missing acknowledgement | Use `SUMNER` on `TC_R052` in an attended/passed synthetic session with no participant response. Test the +2 and +5 Zurich-date rules once each and the later open-case queue. Record message ledger IDs and inbox evidence. No completion notice, proof, or skill update should be issued. Historical dates and mail sends require a separate connected approval and must remain visibly `[DEMO]`. |
| Archive failure/retry | Complete source responses, interrupt or damage only a disposable local archive copy, and show `archive_error` or pending. Confirm no skill raise or completion notice. Rerun the archive helper and record one verified receipt with matching Drive/local PDF hashes. Preserve the failed-attempt logs. |

For each scenario, set `status` to `pass`, `fail`, or `blocked`, enter `observedAtUtc`, actual IDs, and one or more private `evidence` references. A scenario can have more than one request; put the primary ID in `requestId` and any additional IDs in its evidence notes. Mark each named `checks` entry with `result: "pass"` and an individual evidence reference only after observing it. For `seedAdjustments`, enter `applied: true` and the before/after Sheet evidence after the intentional edit. Keep defects in `defects`. Each `archivePairs` entry needs `personKey`, `caseId`, `proofId`, and `drivePdfId` as well as the local path and hashes; a group success needs two distinct identities whose case IDs appear in `caseIds`. A passed scenario with missing check evidence or too few completed archive pairs remains pending in the verifier. The complete [replay checklist](product/DEMO_REPLAY_CHECKLIST.md) covers individual phase and exception gates within these six scripts.

## Scheduling comparison

Use the same training, participant set, calendar state, and time window for the manual and prototype scheduling runs. Start the timer before selecting the training and stop when the invitation is ready; state any difference in stopping point in `measurements.taskDefinition`. Count each intentional human click, entry, selection, or confirmation once, including corrections. Do not count API calls or automated notifications as human actions. Enter timestamps, observed elapsed seconds, action count, and private screen or log evidence separately for `manual` and `prototype`. Report raw values and the difference; do not extrapolate annual savings.

## Private recording

After one connected happy path passes, capture the full flow from need entry through the final notice, including owner, trainer, and participant handoffs; matrix change; and both archive references. Save raw footage under ignored `data/demo-recordings/<run-id>/`. Link it in `recording.relativePath` and set `recording.requestId` to the demonstrated request. Play it back from start to finish and confirm that all steps and text are readable, the intended accounts are visible where needed, and the ending notice and both archive references can be found. Only then set `completeAndReadable: true` and `playbackVerifiedAtUtc`. Keep original footage and any edited copy out of Git and public sharing.

## Release gate

The local verifier can check fixture bounds, recipient allowlist entries, private recording path, observed measurements, and recorded archive hashes. A human still must inspect Google assets, Forms verified-email settings, Calendar guests, delivery ledgers, production matrix boundaries, and playback. Mark `gate.connectedReplayVerified` only after all six connected scenario results and the recording have been reviewed. Record open production-QM decisions separately from prototype defects; passing the demo is not operational approval.
