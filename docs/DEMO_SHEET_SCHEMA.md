# Demo Sheet schema

The Google Sheet used by the prototype is synthetic and marked `[DEMO]`. Local source files define the contract; live asset IDs and account configuration stay in the ignored private handoff.

## Version 12 (acknowledgement reminders and open cases)

`setupDemo()` adds empty `MessageLedger` and `FollowUps` tabs without changing existing cases, proofs, or skills. A daily 09:00 Europe/Zurich trigger calls `processAcknowledgementFollowUps()`. The processor uses the training date in Zurich: one German reminder becomes due on local date +2 and another on +5. It rereads the live trainer result, participant acknowledgement, verified responder Form, assigned account, and Calendar event under a script lock. A cancelled event, absent or failed participant, accepted acknowledgement, unverified Form, or address outside the private four-account fixture blocks sending. If an unattended run first executes after day +5, it sends the day-5 reminder only; it does not send both reminders together.

`MessageLedger` stores a stable key `ack_day_<2|5>:<case_id>:<session_id>`, template version, request/case/session IDs, recipient, due and attempt times, sent time, delivery state, error summary, and `[DEMO]`. It reserves the key before calling `MailApp`. `sent` is not retried. A send exception or interrupted reservation becomes `unknown` and requires manual inspection because delivery cannot be inferred safely; quota exhaustion before reservation stays pending. The daily trigger has its own installer and does not alter the skill update trigger.

After local day +5, an unresolved attended and passed case appears as **open** in the Process & Quality view even if its Form has not been verified, so the missing link is visible. `FollowUps` records an owner action (`note`, `request_link`, or `arrange_follow_up`) with a short note and timestamp. Requesting a link records a task for Process & Quality; it does not create or email a new Form. None of these actions accepts a participant acknowledgement, creates a proof, or changes a skill level.

## Version 11 (audited synthetic skill update)

`setupDemo()` adds the empty `SkillUpdates` tab without changing the existing `Skills` values. An owner-only action accepts a person case only when its trainer reports show attendance and pass for every required phase, its participant responses are accepted and tied to the assigned verified Google accounts, its original proof source hash still matches, and `Proofs.status` is `archived_verified`. Exactly one verified `ArchiveReceipts` row must match the proof/version, case/request/person/topic, source hash, Doc/PDF IDs, and equal Drive/local PDF SHA-256 values. The archive receipt represents the local helper's last verification; Apps Script does not inspect the current local disk.

`SkillUpdates` records `idempotency_key`, case/request/person/topic, previous and target levels, proof ID/version/source hash, archive verification time, application time, status, reason, and `[DEMO]`. The key is `SKILL-<proof-id>-v<version>`. The action uses a script lock, rereads the live `Skills` cell, and writes the target only if it still equals the case's original level. It never awards level 4. A changed level is shown as a conflict for Process & Quality to review in the demo Sheet; it is not overwritten. The ledger starts as `pending` before the matrix write and becomes `applied` after it. A retry can finish an interrupted pending transition without creating another row or raising the level again. Replaying an already applied case returns its historical result, even if a later separate training advanced the person's current level. Opening or refreshing the admin view reconciles ready cases; `installSkillDailyProcessor()` adds one daily 09:00 Europe/Zurich retry trigger using the existing trigger permission. The admin UI shows waiting, ready, conflict, pending, and applied states; it sends no completion notice in this increment.

## Version 10 (dual archive receipt)

`setupDemo()` adds an empty `ArchiveReceipts` tab and preserves existing proof rows. Each receipt is keyed by proof ID/version and stores the case, request, person, topic, source fingerprint, Drive Doc/PDF IDs, SHA-256 of the downloaded Drive PDF and local PDF, SHA-256 of the DOCX snapshot, local file and manifest paths, verification time, status, and `[DEMO]`. A local Python helper rereads the register and Drive folder hierarchy, downloads the exact Drive PDF bytes, exports the native Doc to DOCX, verifies both local files, and writes one receipt before changing `Proofs.status` to `archived_verified`. It also builds `archive/index.csv` for topic/person lookup. The helper uses a separate ignored owner OAuth credential; credentials do not enter the evidence tree or repository.

Missing or corrupt local evidence sets `archive_error` when Google is reachable. Without local connectivity, a first attempt leaves `pending_local_archive`; a previously verified remote receipt can become stale until the helper runs again. A repair rerun validates the same proof ID, version, source fingerprint, and Drive IDs before replacing damaged local bytes. Neither the receipt nor status changes the skill matrix or sends a completion notice. The later skill gate must require both `Proofs.status = archived_verified` and a matching verified receipt, with any offline/local freshness requirement made explicit.

## Version 9 (individual Google Doc and PDF proof)

`setupDemo()` adds an empty `Proofs` tab. Each row stores a deterministic proof ID, version 1, request/case/person/topic IDs, a SHA-256 fingerprint of the validated source model, creation time, Drive topic-folder ID, Google Doc ID, PDF ID, status, and `[DEMO]`. `pending_creation` marks an interrupted write; `pending_local_archive` means the Doc and PDF exist in Drive, while the local duplicate has not yet been checked. The later archive handshake changes that status; proof creation itself never marks archive verification or updates a skill.

The proof action validates every phase required by the topic before writing: booked Calendar event and its Sheet receipt, assigned trainer's accepted attended/pass Form response, and assigned participant's accepted affirmative response after the trainer report. It rereads each original Google Form response by ID and compares the account, timestamp, and answer with the Sheet. A missing practice phase, wrong account, changed matrix entry, or mismatched event blocks creation. The Form's manually reviewed **Verified** setting cannot be rechecked by this Apps Script project; the owner must keep that setting unchanged.

Drive stores `evidence-archive/<topic-id>/<request-id>/<person-key>/PRF-...-v1 [DEMO]` as a native Google Doc and matching PDF. The proof records the synthetic persona, assigned Google test account, and typed name as separate fields. The source catalogue contains a material filename but no separate version field, so the proof prints `Nicht dokumentiert` for the material version. Rerunning the action checks the same source fingerprint and reuses its Doc/PDF IDs. A changed source requires an explicit corrected proof version; version 1 is never silently overwritten. Admin source links point to the Forms response views and Calendar event, not respondent edit links.

## Version 8 (individual participation acknowledgement)

`setupDemo()` adds empty `ParticipantForms` and `ParticipantAcknowledgements` tabs without changing existing bookings, trainer reports, or skill values. `ParticipantForms` maps one invited session and person case to one German Google Form, the assigned account, a stored responder URL, and the time and owner account that reviewed Google's **Verified** email collection setting. Preparing the same case again reuses its Form. The responder URL stays out of the admin queue until Process & Quality records that review; the queue exposes the editor link and review action. FormApp's email toggle alone is insufficient on the owner's personal Gmail account, and the script cannot detect a later change to the Verified setting.

The participant Form requires the affirmative participation checkbox and a typed name. `ParticipantAcknowledgements` stores each processed response ID, Form/request/session/case/person IDs, respondent email, UTC timestamp, typed name, affirmative value, disposition, reason, and `[DEMO]`. The assigned account, stored Form context, post-session time, trainer pass, and review timestamp determine acceptance; typed name is captured as an assertion, not used to identify the account. A practice acknowledgement additionally requires that person's linked theory trainer pass. A Form submit trigger processes responses, and the admin refresh replays retained responses after interruptions. Replay of the same response ID does not append a row; a later response after one accepted confirmation is rejected. Wrong accounts, responses before review or trainer release, missing affirmative answers, and unanswered cases remain open. No proof, archive, or skill value is created in this increment.

## Version 7 (trainer assessment)

`setupDemo()` adds empty `TrainerForms` and `TrainerAssessments` tabs without changing existing rows. `TrainerForms` maps one `session_id` and `case_id` to one Google Form, its assigned trainer key and email, a responder URL, `verified_at`, and `verified_by`. A group session gets a separate form for each participant. Repeating preparation returns the same Form. The Form asks in German for attendance, result, a note or next step, and an attestation; the assignment and identifiers come from the Sheet rather than editable answers.

**Prototype identity gate:** With the owner's personal Gmail account, Apps Script `FormApp.setCollectEmail(true)` created a Form using `Responder input`, an editable email field. The script's default Cloud project returned `SERVICE_DISABLED` from the Forms REST API, so code cannot set or read `emailCollectionType: VERIFIED`. Process & Quality must open each new Form's Google Settings, select **Verified**, then explicitly confirm that inspection in the admin UI. The responder link remains hidden until the owner account records the check and its timestamp. Responses submitted before that timestamp are rejected. The code checks that the reported email matches the assigned trainer, but it cannot independently attest the Form mode or detect a later change to it. Before a later use, Process & Quality must recheck the setting. A standard Cloud project migration or another reliable identity integration is required before treating this as a fully automated or production identity gate.

`TrainerAssessments` retains one row per processed Form response with the raw response ID, Form ID, session and case IDs, person key, respondent email, UTC submission time, attendance, result, note, attestation, disposition, reason, and `[DEMO]`. A form-submit trigger processes new responses; a manual reconciliation can replay retained Form responses after a trigger interruption. Replaying a response does not append a duplicate. A second response to the same case is rejected pending an explicit correction process. Only an accepted `attended` + `passed` row releases that phase to participant acknowledgement. Absence, follow-up, and not-assessed results stay open. Calendar RSVP never substitutes for a trainer report, and no skill value changes in this increment.

## Version 6 (Calendar RSVP monitoring)

`setupDemo()` adds an empty `SessionRsvps` tab. Each row is keyed by `session_id` and `case_id` and stores `person_key`, `calendar_event_id`, the Calendar guest `response_status`, `checked_at` in UTC, the current `flag`, `flagged_at` in UTC, and `[DEMO]`. The monitor writes one row per invited person and session phase, including each member of a group. Repeated checks update the same row. A declined guest gets a `declined` flag; an unanswered (`needsAction`) guest gets an `unanswered` flag starting on the business day before the Zurich session date. Other RSVP values keep no flag. A changed response updates or clears the current flag.

The owner event is read without changing its guests or booking. The monitor verifies the event ID, demo session metadata, times, and exact guest email before recording any response. Missing or inconsistent Calendar data is shown as an error and never interpreted as acceptance or attendance. Process & Quality's RSVP queue links each flag to its person case; replacement scheduling remains a later explicit action. A daily 09:00 Europe/Zurich Apps Script trigger can maintain the queue automatically after the owner grants `script.scriptapp` and installs the trigger. Loading or refreshing the admin page also performs a check. RSVP does not change `ParticipantCases.status`, trainer assessment, or skill level.

## Version 5 (Calendar booking receipt)

`Sessions!L:O` adds `calendar_event_id`, `start_utc`, `end_utc`, and `calendar_event_url`. `setupDemo()` appends these headers to an existing version 4 sheet without changing session rows. The booking action writes these fields and changes the session status from `planned` to `invited` after it verifies the Calendar event. UTC timestamps are stored as ISO strings; the event itself is created in `Europe/Zurich` with the date's actual offset.

Each session has a stable Calendar event ID derived from its session ID. A retry checks that event first, then repairs an incomplete Sheet receipt if needed. A different selected slot, missing calendar access, changed event, or overlapping booked phase is rejected. Practice may be invited after its linked theory event is booked and must start no earlier than theory ends. Passing theory remains a separate later completion requirement.

## Version 4 (mode and phase plan)

`Requests!H` stores `mode` (`group` or `individual`) when a phase plan is saved. Existing draft rows keep their IDs and a blank mode until then. `Sessions` stores `session_id`, `request_id`, `phase`, `phase_order`, `mode`, `trainer_key`, `duration_minutes`, `theory_session_id`, `status`, `created_at`, `demo_marker`. `SessionCases` stores `session_id`, `case_id`, `request_id`, `person_key`, `demo_marker`; a group session links to multiple person cases. Both new tabs are created empty. Session status is `planned` only in Increment 03. The practice row points to its theory session, and target completion requires verified passes for every phase linked to the case, including theory.

`setupDemo()` migrates version 3 by adding only the `mode` header in `Requests!H`, preserving every existing row and cell in A:G, and then creates the two new tabs. Repeated setup checks headers without duplicating tabs. A plan save uses a script lock and deterministic session IDs; repeating the same save returns the existing plan, while conflicting assignments fail. The private fixture's topic and skill values do not change.

## Version 3 (persona aliases)

| Tab | Columns | Purpose |
| --- | --- | --- |
| `Topics` | `topic_id`, `display_name`, `source_material`, `theory_required`, `practice_required`, `theory_minutes`, `practice_minutes`, `group_suitability`, `progression_rule`, `demo_marker`, `configured_target_level` | Five demo topics. For the two `0→1→2→3` topics, target selection follows the chain and the configured target cell is blank. For the other three, the configured target is explicitly `1`. |
| `People` | `person_key`, `email`, `demo_role`, `demo_marker`, `persona_id`, `display_alias` | Four agreed test identities. Persona IDs and display aliases come from the private fixture; `person_key` remains the durable case reference. |
| `Skills` | `person_key`, `topic_id`, `skill_level`, `status_mark`, `demo_marker` | One current synthetic level per person and topic. Intake never writes this tab. |
| `Requests` | `request_id`, `action_id`, `topic_id`, `target_level`, `status`, `created_at`, `demo_marker` | One draft row per browser save action. `action_id` is the retry key; `created_at` is ISO UTC. |
| `ParticipantCases` | `case_id`, `request_id`, `person_key`, `current_level`, `target_level`, `status`, `created_at`, `demo_marker` | One separate draft case per selected person, linked to the request. |

The request ID is `REQ-` plus the action UUID in uppercase. A case ID is `CASE-` plus the same UUID and the stable person key. Saving a request rechecks the live matrix under an Apps Script lock; a retry with the same action ID returns the existing draft. Draft creation does not change `Skills`.

The persona aliases are display metadata only. They do not assert that a test account belongs to the named report persona or change its synthetic matrix level. The source mapping is recorded in the ignored local handoff; no account-specific alias mapping is in public source code.

## Migration from version 2

`setupDemo()` calls `migrateDemoSchemaV2ToV3_()` before checking headers. It verifies the four stable person keys, appends `persona_id` and `display_alias` to `People!E:F` from the ignored fixture, and leaves columns A:D and every `Skills`, `Requests`, and `ParticipantCases` row intact. A repeated setup validates the version 3 headers and does not append duplicate data. A separate one-cell demo-role copy edit made the coach label gender-neutral; stable keys, emails, and skill values were preserved. The ignored JSON fixture, generated private Apps Script fixture, and local workbook builder use the same columns.

## Migration from version 1

`setupDemo()` calls `migrateDemoSchemaV1ToV2_()` before the alias migration. The version 2 migration verifies all five existing topic IDs, appends `configured_target_level` in column K, writes blank for the two progression topics and `1` for the other three, then `setupDemo()` creates the empty `Requests` and `ParticipantCases` tabs with headers. It leaves every existing `People` and `Skills` row intact and does not reset manually corrected matrix entries. `resetDemoFixture()` remains an explicit reset of the three original data tabs; it does not erase draft records.
